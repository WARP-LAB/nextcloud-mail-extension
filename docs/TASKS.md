- **T23: Style the links in the email's HTML.** Today the extension writes plain HTML with no styling: each file's block is `<div><a href="…">name</a> (size, link expires …): <a href="…">Overview</a> · <a href="…">Download</a></div>`, so links look as the recipient's mail client shows them, and the block inherits whatever the surrounding HTML sets. The user's request: the app's settings get a "Styling" section with a switch, off by default. When it's on, the user can set:
  - for each file's block: a background colour (transparent by default), a border colour and a corner radius;
  - for the file name's link: a text colour and a hover colour;
  - for the Overview, View and Download links: a text colour and a hover colour;
  - for the details in brackets, the size and expiry: a text colour.
  - The plain text is never styled. Anything else is the user's to add when it's built. Unset values add no style, so the client's defaults stay.
  - **How it would work:** colours, border and radius as inline `style` attributes, which mail clients keep. Hover colours need a `<style>` block with `:hover` rules, which some clients strip, Gmail and Outlook among them, so hover works in Apple Mail but not everywhere. The settings could use SwiftUI's `ColorPicker`, with the colours stored as hex, and a preview of a block.
  - **Open questions for the user:** whether to keep hover colours, given that limit; which blocks are styled, each file's only or also the links for all files and the password notice, and with "Below your text" the list as one block or each file's block; the border's width and the padding inside the block, which a background or border needs; and whether to offer colours for dark mode, where fixed colours may clash.
  - **Acceptance:** to be written with the user before starting.
- **T22: Tag an email's files on Nextcloud, so they can be found later.** Findings in `docs/NEXTCLOUD.md`, "Share labels and tags": share labels can't be searched, while collaborative tags can be browsed in the Files app's Tags view. The user's decisions: the tag is named "MailShare" by default, set in the app's settings, with a switch to turn tagging on or off, off by default. Tagging must never stop a send: when it fails, as when an admin restricts tag creation or the tag is missing, skip it quietly. When creating the tag fails, don't fall back to an existing tag of that name. Open question for the user: whether to tag each file or only the email's folder, which costs one request per email. Labelling each share as well would cost no extra request.
  - **Acceptance:** to be written with the user before starting.
- **T17: Show the extension as NextcloudMail.** macOS's Local Network prompt names the extension “NextcloudMailEx”: most likely the process name, which macOS cuts to 15 characters (`pgrep -l` showed the old app as "NextcloudAppleM"), taken from the executable `NextcloudMailExtensionPlugIn`. So set the extension's executable name to `NextcloudMail`, keeping its bundle ID and possibly its `.appex` name, rather than only `CFBundleName`, which the executable doesn't use. The executable's path is what the Local Network rule is tied to, so macOS asks again, and the "NextcloudMailExtensionPlugIn" entry stays in the list for good. Which name the list shows, the executable's, the bundle's or the `.appex`'s, is unknown today, because all three match.
  - **Acceptance:** after a fresh install on a clean state (uninstall, restart, reinstall), macOS asks for “NextcloudMail”, what the Local Network list shows is recorded in `docs/MAIL.md`, and the setup help, the offline error, `docs/MAIL.md`, TESTING and the website's Installing steps quote the names macOS shows.
